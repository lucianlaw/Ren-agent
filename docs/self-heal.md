# 自举修复协议

> 这套协议要解决的问题：让 ren agent 承担重复性的 bug 修复，同时保证
> 每一次「它说修好了」都能被复核，每一次「它修不了」都变成一次能力升级。

## 一、链路

```
生产实例（多人使用）
   │  标准报错 → data/incidents/YYYY-MM-DD.jsonl（按签名归组）
   ▼
工单（同一个签名 = 一张工单）                    ← 第六节
   │
   ▼
ren agent 分析：这个 bug 该谁修？
   │
   ├─ 判「自己修」 → 改 dev 实例的代码 → 补回归测试 → 跑自证（红→绿）  ← 第十节
   │                              │
   │                              ▼
   │                        我复核修复单
   │                              │
   │                              ├─ 通过 → 标 verified → 你点上线
   │                              └─ 不通过 → 打回（证据一起作废）→ 见第三节
   │
   └─ 判「我修」 → 我判断它为什么修不了 → 分析能否补上这个能力 → 见第四节
                                  │
                                  └─ 补不上 → 我完成修复
```

四段已经落地：① 看得见（报错采集）② 有地方改且进不去（dev 闸门）
③ 能领取（工单）④ 能自证（红→绿自己复跑）。

## 二、什么算「修完了」

**没有新增回归测试的修复，不算修完。**

这条不是流程洁癖，它同时解决三件事：
1. 证明 bug 真的没了（不是「看起来好了」）；
2. 防止同一个 bug 回来；
3. 逼它先把根因想清楚——想不清根因，就写不出能复现它的测试。

修复单必须包含：

| 字段 | 要求 |
|---|---|
| 签名与次数 | 哪个签名、多少条、跨几个账号、首末次时间 |
| 根因 | 一句话，指到 `文件:行`。说不出来就打回，不许交补丁 |
| 改动 | diff 摘要 + 文件数。超过 3 个文件必须人工过一眼 |
| 新测试 | 测试名 + **红→绿证明**（不是它贴的输出，见第十节） |
| 闸门 | 全量通过的项数与用时 |
| 风险 | 低 / 中 / 高 |

**「贴出来」这个词已经过时了。** 从第十节起，红→绿由我们复跑得出，
它贴的终端输出不作为证据——那段文字是它自己写的。

## 三、我复核出问题时：分析「它为什么错」

不许直接改它的补丁。先归类，因为不同的错因对应不同的修补方式：

| 它错在哪 | 表现 | 怎么修 |
|---|---|---|
| 根因判错 | 测试绿了，但改的是另一处 | 补一条「同签名必须同根因」的校验 |
| 只解决表面 | 加了 try/catch 把错吞了，没改逻辑 | 回归测试必须断言「错误不再发生」而不是「没有抛异常」 |
| 改得不完整 | 一个调用点改了，其他没改 | 加一条源码级断言（所有调用点必须一致） |
| 越界改动 | 顺手改了不相关的文件 | 收紧允许改动的目录与文件数上限 |
| 测试作弊 | 测试里绕开了真实路径 | 复核只看「红→绿」，不看它自己写的测试是否合理 |

**每次复核失败都要落一条记录**：它错在哪一类、这次用了什么约束拦住。
约束攒够三条以上，就把它们写成自动检查（进闸门），而不是靠我每次看。

## 四、它判「我修」时：先问「为什么它修不了」

这是最容易亏掉的一步。**不要直接接手，先分类**：

| 原因 | 例子 | 能否补 |
|---|---|---|
| 信息不足 | 只给了签名，没有复现步骤 | **能补**：工单里补「发生前的最后三步操作」 |
| 无诊断能力 | 模型通道被拦，它不知道 WAF 是什么 | **能补**：把已知成因写进错误码的说明（`E_LLM_GATE` 的 `zh`） |
| 观察者盲区 | 它看不见自己为什么没被正确调用 | **不能补**：必须外部视角 |
| 需要连续换假设 | 六组探针才定性 WAF 是内容拦截 | **不能补**：它每一轮重新读上下文，没有「这个方向试过了」的记忆 |
| 权限红线 | 动鉴权、计费、删除、路径围栏 | **不许补**：见第七节 |

只有「不能补 / 不许补」才该落到我手上。其余三种要回到第一节，
先把能力补上再让它重试——**否则它会永远判「我修」，而这条链路的七成价值就没了。**

## 五、dev 实例：只有你能进，且不碰生产

它改代码的地方。两条约定：

1. **只有维护者本人能访问** —— 因为它有改源码的能力；
2. **只用 dev 自己的数据** —— 在 dev 里删掉的东西必须真的是可丢弃的。

这两条没有写在文档里让人记，而是写成了**启动条件**（`lib/devinfo.js`）：

| 判据 | 不满足时 |
|---|---|
| `HOST` 必须是 `127.0.0.1` / `localhost` / `::1`，且必须显式写 | 拒绝启动 |
| `PORT` 必须显式、合法、且不是 8080（生产口） | 拒绝启动 |
| `WORKSPACE_DIR` / `REN_STATE_DIR` / `AUDIT_DIR` / `INCIDENT_DIR` 必须逐个显式设，且都在 `REN_DEV_ROOT` 下 | 拒绝启动 |

拒绝的退出码是 **2**，和「代码炸了」的 1 分开——运维脚本里这是两件事。
不满足就 `console.error` 说明原因再退，不打印「已启动」，也不监听任何端口。

**为什么要求「显式」而不是给默认值**：这四个目录的默认值恰好就是生产在用的那一份。
默认值最坏的形态不是报错，是「一切看起来都正常，只是数据是真实的」。

**启动方式**：

```
npm run dev                          # 代码用当前目录，数据放 ../.ren-dev
npm run dev -- --port 8091
npm run dev -- --dir ../.ren-dev/work # 跑 worktree 里那一份（第二步做出来后）
```

`scripts/dev.mjs` 会把 `REN_DEV_INSTANCE=1`、`HOST=127.0.0.1` 和四个目录全部写死，
不接受「临时改成 0.0.0.0 试试」——要对外开放就走发布流程，不要暴露开发实例。

**人在外面怎么访问**：不要改绑定，用 SSH 隧道
（`ssh -L 8090:127.0.0.1:8090 <host>`）。把绑定改成 `0.0.0.0` 就等于把「改生产代码」
的权限挂到公网上，而且这种改动在事后没有任何痕迹——隧道至少还是本人的一次登录。

**怎么一眼认出是 dev**：`/api/health` 返回 `dev: true`，启动日志第二行有
`⚠ dev 实例：只绑回环`。dev 和生产的界面长得一模一样，没有这一行，
在 dev 上点了一圈以为处理了真实数据，是很容易发生的事。

## 六、工单：从「统计」到「能被领取的任务」

`/api/incidents` 给的是**事实**（现算的统计），`/api/tickets` 给的是**事实 + 状态**。
只看得见前者的人会得到一个结论：每天都是同样的错，但没人知道上周那张单子处理了没有。

### 状态机

```
open ──领取──> claimed ──交修复单──> fixed ──复核通过──> verified
  │              │  ↑                 │
  │              │  └──复核打回────────┘
  └──判为噪音──> dropped ──复发──> open
```

规则：

- **不许跳步**。`claimed → verified` 会被拒。跳步等于「修好了」这件事没法统计。
- **`fixed` / `verified` / `dropped` 必须带一句说明**。没有说明的「修好了」不可复核——
  一个月后没人知道当时改了什么、为什么这么改。
- **`verified` 是终态**，但复发不改状态，只打 `reopened` 标记。
  修好过又犯，比没修过更值得看：说明当时的修复只压住了症状。
- **判掉的噪音默认不出现在列表里**（`?dropped=1` 能查回来）。否则真 bug 会被
  「断网时的正常失败」淹掉。

### 复现步骤从哪来

从审计日志取「报错前 10 分钟、**同一账号**的最后 8 次工具调用」。
时间窗口只往前，不往后——把报错**之后**的操作当复现步骤，因果就反了。

三种拿不到的情况，**一律明说，不编**：

| 情况 | 原因 |
|---|---|
| 匿名上报（没有账号） | 登录页崩了、前端还没拿到身份，关联不到操作序列 |
| 审计里查不到 | 过了保留期，或这一步根本没走到工具调用 |
| 没有时间戳 | 无法回溯 |

编一个假的复现路径比没有更坏：它会带着人往不相干的地方查。

### 任务模板

`/api/ticket?sig=…&task=1` 返回的那段文字，是这一层的产出物。三段缺一不可：

1. **事实**：次数、首末次、影响账号数、路由、出错位置
2. **复现**：操作链条 + 「↓」+ 报错点；拿不到就写清楚为什么
3. **边界 + 验收**：红线清单**前置**在任务里，验收要求「指到 文件:行」和「红→绿」

红线前置的理由：等它改完再拒绝，等于浪费一整轮推理，而且它改的那一版已经进了工作区。

### 一条实操教训：预期内的拒绝不许进工单表

5xx 自动采集分不清「出故障」和「按设计拒绝」。上线第一天本地 7 条真实报错**全部**
是 `POST /api/upload → 507`（用户配额满了），得分 31.5 排第一，而它没有任何代码要修。

这类条目一旦进表会**永久霸榜**——5xx 严重度最高，而它永远不会被修掉。
解法不是采集端猜，而是让 handler 显式声明（`expectReject(res)`）：谁产生响应，谁最清楚。

代价是标记必须**少**。一旦为了消噪音到处乱标，真故障也会被吞掉——那等于把
「看得见」这件事修没了。

## 七、红线：它不许动的东西

以下代码改了，等于它有权决定「谁能干什么」：

- `lib/authn.js`、`lib/identity.js` —— 身份
- `lib/perms.js` —— 权限档位
- `lib/quota.js`、`lib/points*` —— 计费
- `lib/trash.js`、`lib/purge.js` —— 数据删除
- `lib/tools.js` 的 `within()` / `DENY_PATH` —— 路径围栏
- `server.js` 的 `PUBLIC_API` / `OPTIONAL_AUTH` —— 免登录边界

这类问题它只能出分析，不许出补丁。**一旦允许，一次提示注入就能让它给自己开权限。**

## 八、错误码与分诊归属

`lib/incident.js` 的 `CODES` 表里每条都带 `owner`，它是分诊的**第一层判断**，不是结论：

- `self` —— ren agent 大概率能修（界面、工具实现、参数校验）
- `external` —— 外部依赖或配置（网关、额度、网络），改自己代码没用
- `either` —— 要看具体样本

固定成表的理由：一张能被讨论和修正的表，比每次现判稳定。
现判会飘——同一个错今天说 self 明天说 external，就统计不出「它判断得准不准」。

## 九、这张表本身怎么进化

每次分诊结论和 `CODES.owner` 不一致，就是一次规则修正：

- `owner` 写 `self` 但它说修不了 → 看第四节，能补就补，补不上就改成 `external`
- `owner` 写 `external` 但它修了 → 说明码分错了，或者它比预期强，改成 `self`
- 出现新签名归到 `E_UNKNOWN` → 加一个码，别让它一直堆在未归类里

**判断准确率是可以统计的**：分诊结论 vs 实际谁修，对不上的比例就是这套协议的误差率。
这个数不降下来，「让它自己修」就只是换个人在猜。

## 十、自证：红→绿必须是我们跑出来的

第二节说「没有新增回归测试的修复，不算修完」。但**怎么知道那个测试真的红过**？

它贴的终端输出回答不了这个问题。那段文字是它自己写的，它完全可能：
跑的是另一份测试、把失败说成成功、或者「红」其实是模块不存在。
所以 `lib/proof.js` 不采信任何自述，自己跑：

```
1. 检出修复提交的父提交（临时 worktree，不动当前工作区）
2. 把修复提交里的那份测试原样铺过去
3. 在旧代码上跑 → 必须失败
4. 在修复提交上跑 → 必须通过且 0 失败
5. 结果写进 data/proofs/，结算 fixed / verified 时检查它
```

命令：`npm run prove -- --ticket <工单号> --test test/xxx-test.mjs`

### 为什么用 worktree 而不是 checkout

证明过程不能把正在跑的服务脚下的文件换掉。用 `git worktree` 建两份临时检出，
当前工作区一个字节都不动——测试里专门验了这一条。

顺带解决一件事：**证明跑的是提交，不是工作区**。所以改完没提交时不能自证，
这不是缺陷，是要求——「能复现的那一版」必须有一个可以指认的哈希。

### 四种假绿，每一种都真的会有人这么干

| 形态 | 怎么挡 |
|---|---|
| 测试测不到 bug（旧代码也能过） | `red-fails`：旧代码上必须失败 |
| 把测试掏空（退出 0 但没有断言） | 汇总行 `N 通过 / M 失败` 是唯一凭证，缺了判 `silent`，不算过 |
| 换一份测试去跑，贴另一份的输出 | 测试内容取**修复提交里的那份**，并记 sha256；事后被改，证据作废 |
| 代码根本没改 | `diff-not-empty`：两个提交一模一样直接拒 |

还有一条：**绿不能比红更弱**。修完之后通过的断言数不能少于修之前
（`green-not-weaker`）——少了说明有断言被删，那不是修好，是判据没了。

### 强红与弱红：这一层最要紧的判断

同样叫「红」，可信度差一档：

| 红的原因 | 含义 | 能标 fixed | 能标 verified |
|---|---|---|---|
| `assert` 断言失败 | 测试跑完了，bug 当时确实在 | ✅ | ✅ |
| `load` 模块不存在 | 这个能力原来没有 | ✅ | ❌ |
| `crash` 没跑完就崩了 | **什么也证明不了**，可能只是测试写错了 | ✅ | ❌ |

所以证据里 `red.kind` 是必填项，`strong` 单独一个布尔。
「复核通过」要求强红——否则以后所有新功能都能自称修了个 bug。

**实操推论**：想让红变成强红，回归测试要写成「调用**已存在的**入口，
断言它的行为」。测试一个新模块的新函数，在旧代码上必然只能得到 `load`，
那不是回归测试，是验收测试。

### 打回 = 证据一起作废

`fixed → claimed`（复核不过）会删掉证据文件。不删的话，下一次结算会复用到
上一份过期的绿——**证据是真的，但它证明的不是这一版**。这是「看起来好了」
的第二种形态，比没有证据更难发现。

### 两个工程细节，不做就会变成真问题

**全局串行。** 两个证明同时跑会抢 `.git/worktrees`，互相把对方的 worktree 删掉，
症状是随机失败，而且只在有人连点两次时出现——那种 bug 没人能靠看日志想明白。
现在第二个请求直接 429。

**环境要洗。** 证明脚本在服务进程里跑，而服务身上挂着 `REN_STATE_DIR` /
`AUDIT_DIR` / `TICKET_DIR` 这些指向**生产数据**的变量。被测测试如果偷懒读了它们，
一次「证明」就会往真实数据里写东西。宁可让测试因为缺变量自己报错。

### 一个真实仓库上才暴露的盲点

`build.json` 是构建产物、被 gitignore。worktree 里没有它，测试一读就
ENOENT，分类器只能报 `crash`——看上去像代码坏了，实际是环境不完整。

解法是按**那个提交的 package.json** 重新生成一份（不是拷当前那份：
拷过去会写着别的版本号和别的提交号，测试拿它做断言会得出荒谬结论），
并在证据里记 `seeded`，让复核的人知道有东西是造出来的。

## 十一、修复工作区：它到底在哪改

前四步都是基础设施。缺的是中间那段路：**它到底在哪改，改完怎么变成一张能复核的单子**。

### 不在原地改

dev 实例跑的就是这份源码。让它原地改，等于一边跑一边换自己脚下的文件：
下一次 import 拿到的是半成品，进程可能直接崩，而崩掉之后连「刚才改了什么」都重建不出来。

所以每张单子开一个 `git worktree`（`data/repair/wt-<工单号>`，分支 `heal/<工单号>`）：
同一份历史、另一份工作区。改坏了 `abort` 删掉即可，**正在跑的那份一个字节没动**。

### 只在 dev 实例开

```js
REN_DEV_INSTANCE=1 且 HOST 是回环  → 开
其他                                → 503，并把理由讲清楚
```

用 503 而不是 403：403 会被读成「令牌没配好」，而这里不是权限问题，是**这个实例上根本不该有这个能力**。
部署包里没有 `.git`，本来也建不出 worktree——但那是巧合，不是判据。

### 没有 shell

给了 shell，前面所有路径围栏都白做：一句 `cat` 就能读到任何东西。
跑测试由 `prove` 一步代劳，不需要通用命令执行。

### 三道围栏

| 层 | 挡什么 | 例 |
|---|---|---|
| 路径 | 出工作区、绝对路径、`..`、`.git`、`node_modules`、软链逃逸 | `link/secret.txt` → 拒 |
| 文件 | 改了等于「有权决定谁能干什么」，或者能伪造证据 | `lib/authn.js`、`lib/perms.js`、`lib/proof.js`、`lib/repair.js`、`lib/ticket.js` |
| 代码块 | 整份禁太粗、按字符串太糙，所以按**块的边界**判 | `lib/tools.js` 的 `within()`、`server.js` 的 `PUBLIC_API` |

第三层是这里最费劲的一段。`server.js` 里本来就写着 `PUBLIC_API`，
按字符串判会把任何一行改动都算成碰红线；整份禁掉的话，大部分 bug 就都修不了。
所以：**锚点行 + 块边界 + 真的改了哪几行**，三者一起判。

块边界取「锚点行到它对应的收尾行」：`{` 配 `}`、`[` 配 `]`。一行写完的常量（`const PUBLIC_API = new Set([...]);`）
块就是它自己——不然它会一路吃到文件里下一个行首 `}`，等于整份文件禁掉。

### 一个只有真仓库才暴露的坑：上下文行

第一版按 `@@ -a,b +c,d @@` 的范围判「改了哪些行」。git 默认带 **3 行上下文**，
于是「改一个离围栏 3 行以内的普通代码」也会被判成碰到了围栏——几乎等于整份文件禁掉。
正确做法是逐行数：只有 `+` / `-` 开头的行才算改动，上下文行不计。
这条现在有测试钉着（改无关函数 → 放行；改函数体 → 拒；一行常量只算一行）。

### 它只能交到 fixed

`submit` 最多把单子推到 `fixed`。`verified` 是留给人的。

理由和第五节那条一样：**允许它自证自己通过，等于把「谁来判断」也交出去了**。
它能做的是：指到根因、给出测试、跑出红→绿、把 patch 摊开在回执里。
人要做的只有两件：看一眼 patch，自己再跑一遍 `prove`。

### 走一轮长什么样

```bash
npm run dev                                    # 另开终端：dev 实例，只绑回环

node scripts/heal.mjs list                     # 有没有正在修的
node scripts/heal.mjs begin --sig <工单签名>    # 建 worktree + 领单 + 给任务书
node scripts/heal.mjs grep  --key <号> --q "within"
node scripts/heal.mjs read  --key <号> --path lib/tools.js --from 400 --lines 80
node scripts/heal.mjs edit  --key <号> --path lib/tools.js --old "..." --new "..."
node scripts/heal.mjs diff  --key <号>          # 同时报「有没有碰红线」
node scripts/heal.mjs prove --key <号> --test test/xxx-test.mjs
node scripts/heal.mjs submit --key <号> --note "改了什么、为什么"
```

`begin` 的回执里带整份任务书（事实 / 复现 / 红线 / 验收），不用再拼一遍上下文。

### 为什么命令行不算「第二套判定」

判定全在服务端：路径围栏、红线、红→绿、状态机。命令行只做三件事：拼请求、发请求、把回执翻成人话。
它要是能判定，那判定就等于没有——改个参数就能绕过。

## 十二、谁起这一轮

前五步（看得见 / dev 闸门 / 工单 / 自证 / 修复工作区）都是基础设施。
缺的是最后一块：**谁按第一个按钮**。

没有这一层，那五步等同一套没人按的按钮——单子堆着，谁都不知道该先动哪张、
哪张根本不该动。所以这一层只产出两样东西：**选一张**、**说清为什么跳过其余**。

### 第二样至少和第一样重要

「这周一张都没修」有两种完全不同的原因：

- 真没有错
- 全被规则挡掉了（都是 external、都试满三次、都不在额度里）

只报第一种，第二种会被当成第一种，然后你就再也不看这个数字了。
所以每次分诊都落一条决策记录（`data/repair/decisions/<日期>.jsonl`），
`npm run heal -- decisions` 能直接回答「挡掉最多的是什么」。

### 五条克制

| 规则 | 阈值 | 为什么 |
|---|---|---|
| 只派 `self` | — | external 不是我们的代码（模型网关、网络），派出去等于对着改不动的东西烧一晚上；either 要人先判归属 |
| 单张最多试 3 次 | `maxAttempts` | 同一份代码 + 同一份上下文，重试大概率同样的结果 |
| 两张之间隔 6 小时 | `cooldownMs` | 每次失败都要跑一遍一分钟起的全量测试 |
| 同时只开一张 | `active` | prove 跑全量测试，两个 worktree 会互相踩 |
| 一天最多 5 张 | `dailyBudget` | 这是给机器留的余量，不是效率指标 |

阈值都在 `lib/triage.js` 的 `POLICY` 里。它们是**经验值**，不是定理：
调了以后选出来的东西会明显不一样。

### 一个顺序问题（实测踩到的）

回执原来先挑新的、挑不到才说「在修」。于是「只有一张单、而它正在被修」
会回一句**「没有可派的单子」**——同一件事，听起来像没事可做，实际是正在做。
这两句对下一步动作的引导正好相反，所以现在先看「有没有在修的」。

### 复发优先

修好之后又犯了，比没修过更值得看：那次修复只压住了症状。
判据是「结算时间早于最后一次报错」——所以 `settledAt` 和 `lastMs` 必须是同一个时钟来源，
否则「复发」会被误判成「没修过」或者反过来。

### 自动到什么程度

`next` 会真的开一张（建 worktree、领单、给任务书），但它**不改代码**——
改那一步仍然要一个 agent 去做。这一层只负责把「该干什么」摆到桌面上。

想让它守着：

```bash
node scripts/heal.mjs next --wait          # 有新单子就开，没有就每分钟看一眼
```

`--wait` 循环里只发 `triage`（选而不开），有得选才发 `next`。
不然每轮都会真开一张，把额度烧在一个正被人看着的屏幕上。

### 为什么不在命令行里判

判定全在服务端：归属、次数、冷却、额度、单飞。
命令行要是能判定，那判定就等于没有——改个参数就绕过去了。
它只做三件事：拼请求、发请求、把回执翻成人话。

## 十三、那道没人设的闸：dev 的数据写进了生产

前三节都在讲「怎么让它自己修」。这一节讲一次**差点没被发现**的泄漏——
它不报错、日志正常、health 也正常，唯一的症状是线上开始出现没发生过的工单。

### 症状

上线 `0.8.15` 之后核对 health，分诊快照里写着：

```
rounds=2  picked=1  began=1
last: 接着 6927c393ef9f3e88 在修
```

那个 16 位号是**我在 dev 实例上演示时**造出来的。线上的报错表里根本没有这张单。
再往下看，`data/tickets` 里有 3 个状态文件，而线上只该有 1 张单。

### 根因是两件叠在一起的事

**一、新库没被加进闸门。** `lib/devinfo.js` 那张「dev 自己的数据目录」表里
原来只有四项：工作区 / 状态库 / 审计 / 报错。后来加了工单、修复工作区、自证证据
三个库，各自都有 `*_DIR`，但**没人回来加一行**。于是它们落回默认路径
`data/<库>`——而那正是生产在用的那一份。dev 闸门照样报「合格」。

**二、`data/` 在 .gitignore 里，所以发布闸门看不见它。** 「工作区干净」那道门
跑的是 `git status`，而 `data/` 被忽略；但发布工具传的是**目录**，不是 commit。
于是本地跑过的一切——工单状态、修复快照、分诊决策、审计日志——一起打包上线，
在线上装成生产数据。顺带 `workspace/` 里 223 个本地测试残留也是这么走的。

最坏的一条不是「多出假数据」：`data/incidents/<日期>.jsonl` 同名，
**会覆盖线上那一天的真实报错**。而 5xx 采集正是整套自愈的入口。

### 两处修，缺一不可

1. `lib/devinfo.js` 的目录表从四项扩到七项，`scripts/dev.mjs` 对应设好
   `TICKET_DIR` / `REPAIR_DIR` / `PROOF_DIR`。dev 实例从此写不到生产目录。
2. 发布闸门加一道：`data/`、`workspace/`、`.ren-state`、`.ren-dev` 下
   不许有任何文件（说明性文件除外）。判定放在 `lib/deployguard.js`——
   写在 `release.mjs` 里就没法测，而「闸门自己没被验过」正是这类洞的成因。

报错文案刻意不给 `rm -rf`，只给「挪到部署目录外面留一份」：哪些是残留、
哪些是有人特意留下对照的，只有人能判断。

### 值得记住的一条

> 闸门报「合格」比没有闸门更坏。

没有闸门时人知道自己在裸奔；闸门报合格时，人会拿它当结论。
所以**新开一个落盘目录 ≠ 加一个常量**：要回去把闸门的名单也加一行。
这条现在有测试钉着（`devinfo-test` 直接断言 `DIRS` 是那七个键，
`deployguard-test` 直接断言每个库的默认路径都在名单覆盖范围内）。
