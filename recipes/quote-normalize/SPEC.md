# 配方：报价表折算排序（quote-normalize）

> 这是「配方池」的第一个样本。它解决的问题不是「让模型算得更准」，而是**让算术根本不由模型来做**。

## 为什么拆成两段

模型做长除法会错，而且错得很自信——它不会告诉你「我不确定」，它会给你一个看起来合理的 3.4371。
而报价折算的每一个数字后面都跟着一张订单。**算术出错的代价是签错合同，这个风险不能交给概率。**

但反过来，让脚本去读懂「一套 4 个、运费到付 800 一车 6000 个、不含税」这种自由文本，同样不现实。

所以分工是：

| 谁 | 干什么 | 为什么 |
|---|---|---|
| **模型** | 认表：把备注里的自由文本解析成结构化字段 | 这是理解，模型强项 |
| **脚本** | 算：换算、摊运费、加税、算总成本、排序 | 这是算术，脚本零误差 |
| **模型** | 复核：抽查 2 行的算式，判断是否合理 | 兜底，防止解析错位 |
| **模型** | 写信：把结论写成邮件草稿 | 表达，模型强项 |
| **人** | 发送 | 对外发送是红线 |

## 三段式流程

```
1) 模型读原始表  →  quotes.json（结构化，字段见下）
2) 脚本算        →  python3 calc.py quotes.json  →  折算对比.md
3) 模型复核 + 起草邮件  →  人工确认后发送
```

## quotes.json 字段

```jsonc
{
  "material": "五层瓦楞纸箱 40x30x25cm",
  "need_qty": 8000,          // 本周需求量
  "base_unit": "个",         // 统一折算到的基础单位
  "tax_rate": 0.13,          // 统一税口径（换算成含税）
  "suppliers": [
    {
      "name": "华东包装",
      "price": 3.20,
      "price_unit": "元/个",
      "unit_factor": 1,      // 一个计价单位 = 多少个 base_unit；null 表示「表里没写」
      "freight_per_unit": 0, // 已明确到每单位的运费
      "freight_flat": 800,   // 整车/整批固定运费
      "qty_per_trip": 6000,  // 一车装多少个（摊固定运费用）
      "freight_note": "",    // 运费没量化时的原文，脚本会据此标「不可比」
      "tax_included": true,  // true 含税 / false 不含税 / null 没写
      "moq": 5000,
      "lead_days": 15
    }
  ]
}
```

## 两条硬规则（脚本里已强制）

**规则一：信息不全的不许排名。**
`unit_factor` 缺失、运费没量化、税口径没写 —— 只要沾一条，这家就不进排序表，
单独归到「信息不全，不进排名」，并标明「当前单价只是下界」。

这条是踩出来的：第一版把「3.05 元/个 + 运费 3 元/箱（箱规格未给）」排在了第 1 名。
如果直接采信，就会在一个信息不全的供应商上做决策，而它加完运费很可能就是 3.20。

**规则二：同时排两个序 —— 单价和总成本。**
它们经常不一致。本周的样本里：

- 按单价：华东 3.20 < 南方 3.3674 < 恒通 3.616
- 按总成本：华东 25,600 < 恒通 28,928 < 南方 40,408.80

南方单价最低，但因为起订量 12,000，总成本反而最贵，还多压 4,000 个库存。
**只排单价，等于把最贵的那家推给老板。**

## 调用方式

```bash
python3 recipes/quote-normalize/calc.py quotes.json > 报价对比.md
```

脚本只输出到 stdout，不落盘、不改源文件。落盘由调用方决定（任务里就是模型用 write_file 写）。
